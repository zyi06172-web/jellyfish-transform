## 0. 先读这一节：第5批为什么不合格

第5批画布已经落地（commit `5d0ff57` / `e119d59` / `c1b46df`），React Flow 的用法本身是**正确的** —— `Handle`、`nodeTypes`、`memo` 都没写错。

不合格的唯一根因是：

> `nodeTypes` 只注册了 `{ nuwa: NuwaNode }` 一种。十类内容（角色四视图、6格故事板、镜头分组、关键帧、分镜表、视频……）全部塞进同一个约 50 行的通用盒子里渲染，整个文件 1247 行。

由此产生的具体故障（本批必须全部消失）：

| 现象 | 根因 |
|---|---|
| 所有节点长得一模一样，看不出是什么 | 通用盒子 |
| 6 格故事板只显示 4 张 | `images.slice(0, 4)` |
| 六要素显示不全 | `items.slice(0, 5)` |
| 分镜表是一坨 `<pre>` 文本 | 没有表格节点 |
| 画面比例错（竖屏） | `aspect-[9/16]` 硬编码，与「默认 16:9」的决策矛盾 |
| 节点上没有任何操作 | 没有节点工具栏（无重渲/确认/下载） |

**所以：本批不是「换一个开源画布进来」，而是「把一种节点拆成十种节点」。**

参考实现（架构模板，MIT 许可，可自由借鉴）：`github.com/vercel-labs/tersa`
它节点部分总共只有 1856 行，就做出了 image/text/video/drop 四类各自独立的节点。**注意：它是 shadcn/ui + Tailwind + Next.js，我们是 antd + React 18，因此照搬的是「结构与职责划分」，不是照抄 JSX。** 逐字复制 Tersa 的 class 名和 UI 组件是错误做法。

## 1. 灵魂链路：本批必须端到端跑通的东西

产品的灵魂**不是**首页、不是标题生成、不是 Flova 式的 from-prompt 分析（这些已废止）。灵魂是这条链：

```
① Agent 问答（画布内对话框，贴剧本 → 解析 → 补齐）
      ↓
② 人物资产（四视图）/ 场景资产 / 道具资产
      ↓
③ 手绘故事板（1 页 6 格，1 秒 1 格）
      ↓
④ 文字版分镜表（免费预审，课金前的闸门）  ← 第6批新增
      ↓
⑤ 关键帧渲染（超写实，5 张）+ 渲染版分镜表（真料审片）
      ↓
⑥ 视频生成（Seedance，逐镜头）+ 下载导出
```

**「能用」的定义（验收总则）**：一个不懂代码的人打开画布，只靠画布内的对话框和节点上的按钮，就能把一段剧本走完上面 ① → ⑥，中途每一步都能看清、能改、能重做、能确认，且在真正花钱的两个环节（渲染、出视频）之前有明确的确认闸门。

**不允许出现的交付形态**：骨架、脚手架、demo 数据、TODO 占位、"后续接入"。本批产物必须接的是真实后端与真实模型。

## 2. 六条硬性原则（违反任何一条即整批不通过）

**原则 1：一节点一类型。**
`nodeTypes` 必须注册十个键，每个键对应一个独立组件文件。禁止再出现任何形式的「通用节点」「万能盒子」「根据 data.kind 分支渲染」的单一组件。判定方法：`grep` 全仓库，任何一个节点组件文件超过 400 行即视为没拆干净。

**原则 2：再生成永远开新节点，绝不覆盖。**
（对应 backlog ⑥ 生成历史/回滚）用户点「重渲」「重出视频」时，**旧节点原地保留**，新结果作为一个新节点生成在旧节点右侧（或下方），并从来源节点连一条边过去。画布因此天然成为生成历史。
**只有用户可以删除节点。系统、agent、任何自动逻辑都不得删除或就地改写已有的生成结果节点。**

**原则 3：单一数据源。**
渲染图（关键帧）只生成一次、只存一份。关键帧节点和渲染版分镜表节点**读同一份数据**，分镜表不得为了排版而重复调用一次生图。判定方法：跑一次完整链路，生图调用次数必须与「格数」一致，不得翻倍。

**原则 4：成本闸门。**
两处必须有用户显式确认才允许发起付费调用：
- 渲染关键帧之前（每格 1 张 × 5 张）
- 出视频之前（Seedance，约 ¥5–8 / 8 秒）
未确认前，后端不得收到任何生图/生视频请求。

**原则 5：画面比例来自项目设置，不得硬编码。**
默认 **16:9**（已确认为横屏影视创作路线）。所有节点里的预览框宽高比必须读项目的 `aspect_ratio` 字段。全仓库 `grep` `aspect-[9/16]`、`9/16`、`1584x2816` 等硬编码，结果必须为 0 处（迁移用的历史数据除外）。

**原则 6：六要素永不上屏。**
`six_elements_for_video_model`（主体/场景/摄像机/景别/拍摄手法/灯光）是给视频模型读的结构化数据，**只存在 `node.data` 与数据库里，不在画布上渲染成文字**。画布上给人看的是「一句话总结」。
唯一例外：文字版分镜表（第 9 节）——那是专门为人工审查设计的视图，在那里可以展开。

## 4. 地基三件套

这三个文件写对了，十种节点就都是薄的。写错了，就会重演 1247 行。

### 4.1 `components/nodes/index.ts` —— 注册表

```ts
import { ScriptNode } from './script/ScriptNode';
import { CharacterNode } from './character/CharacterNode';
import { LocationNode } from './location/LocationNode';
import { PropNode } from './prop/PropNode';
import { StoryboardNode } from './storyboard/StoryboardNode';
import { ShotGroupNode } from './shotgroup/ShotGroupNode';
import { KeyframeNode } from './keyframe/KeyframeNode';
import { ShotlistTextNode } from './shotlist/ShotlistTextNode';
import { ShotlistRenderNode } from './shotlist/ShotlistRenderNode';
import { VideoNode } from './video/VideoNode';

export const nodeTypes = {
  script:          ScriptNode,
  character:       CharacterNode,
  location:        LocationNode,
  prop:            PropNode,
  storyboard:      StoryboardNode,
  shot_group:      ShotGroupNode,
  keyframe:        KeyframeNode,
  shotlist_text:   ShotlistTextNode,
  shotlist_render: ShotlistRenderNode,
  video:           VideoNode,
} as const;
```

`nodeTypes` 必须在模块顶层定义为常量（不得写在组件内部，否则每次 render 重建会导致整画布重绘 —— 这是 React Flow 最常见的性能事故）。

### 4.2 `NodeLayout.tsx` —— 共用外壳

所有节点的**边框、标题、连接点、右键菜单、选中态、错误提示**只在这里写一次。节点组件只负责「身体」。

```ts
interface NodeLayoutProps {
  id: string;
  type: keyof typeof nodeTypes;
  title: string;                    // 节点标题，例：「角色资产 · 沈知夏」
  subtitle?: string;                // 例：「四视图 · 已入库」
  width: number;                    // 见第 6 节各节点规定宽度
  status: 'empty' | 'loading' | 'ready' | 'error';
  errorMessage?: string;
  cost?: { tokens?: number; cny?: number };  // 有则在页脚右下角显示「≈¥0.33」
  toolbar?: ToolbarItem[];          // 选中时浮出
  handles: { target: boolean; source: boolean };
  children: ReactNode;
}
interface ToolbarItem { key: string; icon: ReactNode; tooltip: string; danger?: boolean; onClick(): void; }
```

必须包含的通用行为：

- **连接点**：`Handle` 左 target、右 source。`video` 类型 source 为 false（视频是链路终点）。
- **右键菜单**：复制节点 / 居中聚焦 / 删除。删除必须二次确认（对应原则 2：节点是历史）。
- **加载态**：骨架屏 + 转圈 + 「正在生成…」文案，**不得整块变白**；加载中节点仍可拖动。
- **错误态**：红色描边 + 一行人话错误信息 + 「重试」按钮。错误信息要说清「哪一步失败了、怎么办」，不要抛 traceback，不要写「请稍后再试」这种没信息量的话。
- **开发态**：`NODE_ENV === 'development'` 时右键多一项「查看节点数据」，弹窗展示 `node.data` 的 JSON（六要素在这里可见，这不算上屏）。
- **性能**：组件用 `memo` 包裹；`zoom < 0.5` 时进入简化渲染（只画标题条 + 一张缩略图，不渲染网格/表格/video 标签）。十几个重节点同屏必须不卡。

### 4.3 `NodeToolbar.tsx`

选中节点时在节点上方浮出的圆角操作条。每个按钮必须有 tooltip。**只在 `node.selected === true` 时渲染**，不选中不占位、不遮挡。

## 5. 数据契约

`node.data` 一律遵守：**「后端字段名照抄，不在前端重命名」**。已存在的后端字段一个都不许改名。

```ts
// 所有节点共有
interface BaseNodeData {
  project_id: string;
  canvas_id: string;
  status: 'empty' | 'loading' | 'ready' | 'error';
  error?: string;
  created_at: string;
  seed?: number;                  // ← backlog ④：生成时写入，重渲时默认复用
  derived_from?: string;          // ← 原则 2：本节点是哪个节点重渲出来的
  cost?: { model: string; tokens?: number; cny?: number };
}
```

各类型追加字段（字段名对齐现有后端）：

| 节点类型 | 关键字段 |
|---|---|
| `script` | `raw_script`、`parsed: { story_structure, characters[], shots_info }` |
| `character` | `character_id`、`name`、`bible_json`（含 `wearable_accessories` 带位置信息）、`reference_layout: 'four_view'`、`images: { face_closeup, full_front, full_side, full_back }`、`linked_existing: boolean` |
| `location` | `location_id`、`name`、`time_of_day`、`mood`、`style`、`images[]` |
| `prop` | `prop_id`、`name`、`is_wearable`（true 时不单独出图，穿在人物身上）、`image` |
| `storyboard` | `content_json.pages[*].panels[*]`：`index`、`one_sentence_summary`、`six_elements_for_video_model`、`is_blank` |
| `shot_group` | `shots[]`：`shot_index`、`first_frame`、`last_frame`、`duration`、`camera_shot`、`movement`、`composition_anchor`、`screen_direction_guidance` |
| `keyframe` | `frames[]`：`panel_index`、`url`、`seed`、`status`（**逐张独立**，对应 backlog ①） |
| `shotlist_text` | `rows[]`：见第 9 节 |
| `shotlist_render` | 引用 `keyframe.frames[]` + `shot_group.shots[]`，**自身不持有图片资产** |
| `video` | `clip_id`、`url`、`duration`、`resolution`、`aspect_ratio`、`shot_index`、`prompt_used` |

后端如缺对应读接口，本批补齐；已存在的 `GET /projects/{id}/asset-library` 直接复用，不得另造一套。

## 6. 十种节点逐个规格

线框图里的 `[]` 是按钮，`▢` 是图片位。每节点的**宽度写死为规定值**（高度自适应），否则画布上会长短不齐像草稿。

### N1 `script` 剧本节点（宽 420）

```
┌─ 剧本 · 第1章 ───────────────────┐
│ ┌────────────────────────────┐   │
│ │ 婚礼当天，新郎逃婚……        │   │  ← 原文，折叠显示 6 行，可展开
│ └────────────────────────────┘   │
│ ── 解析结果 ──────────────────    │
│ 故事构成  ✓ 已提取              │
│ 角色      沈知夏 / 冷司寒 / 林晚晚│
│ 分镜信息  ✓ 7 个镜头             │
│                    [编辑] [重解析]│
└──────────────────────────────────┘
```
- 三要素（故事构成 / 角色 / 分镜信息）逐项显示「✓ 已提取」或「⚠ 缺失」。缺失项旁边给「在对话框补齐」按钮，点击后聚焦 AgentDock 并自动带出该项的追问。
- 解析走现有 `script_divider_agent.py`。**严禁扩写**：原剧本没有的人物/事件不得出现（这条规则已在源码，前端不得绕过）。

### N2 `character` 角色资产节点（宽 460）—— 本批的门面

```
┌─ 角色资产 · 沈知夏         已入库 ✓ ┐
│ ┌───────────┐ ┌─────┐┌─────┐┌─────┐│
│ │           │ │     ││     ││     ││
│ │  左脸特写  │ │全身正││全身侧││全身背││
│ │           │ │     ││     ││     ││
│ └───────────┘ └─────┘└─────┘└─────┘│
│ 纯白底 · 银色胸针（左胸西装翻领）    │
│ ── 角色圣经 ──────────────────      │
│ 细长杏眼 / 低盘发 / 清冷           │
│                          [展开全文]│
│ [重渲] [局部重渲] [从资产库替换] [↓]│
│                            ≈¥0.33 │
└────────────────────────────────────┘
```
- 布局**严格**：左侧一张大的左脸特写，右侧三张等大全身（正/侧/背）横排。这是已确认的四视图规格，不得改成 2×2 平铺或竖排。
- 背景强制纯白（`pure white studio`）。穿戴类配饰不单独出图，穿在人身上，并在图下用一行文字标出位置（读 `bible_json.wearable_accessories`）。
- **`images` 必须渲染 4 张，禁止 `slice`。** 缺图的位置显示占位框 + 「补渲这一张」。
- `linked_existing === true` 时标题右侧显示「复用自资产库」徽标，且不显示费用（因为没花钱生成）。
- 「局部重渲」= 只重渲被点中的那一张视图（配合 backlog ④ seed 复用，保证其余三张不变）。

### N3 `location` 场景资产节点（宽 380）

```
┌─ 场景 · 婚礼大堂 ──────────┐
│ ▢▢▢▢▢▢▢▢▢▢▢▢▢ (16:9)     │
│ 夜 · 压抑 · 超写实         │
│ [重渲] [加机位] [↓]  ≈¥0.11│
└────────────────────────────┘
```
- 「加机位」对应 backlog ⑤（同一场景多角度资产）。点击后在右侧派生一个新的 `location` 节点，复用同一 `location_id` 与 seed，只变机位描述。**本批把入口和链路做通即可**，后端 `reference_layout` 扩展到 location 分支放在本批最后一个阶段。

### N4 `prop` 道具节点（宽 320）
- 独立道具（捧花、协议书）单独出图；`is_wearable === true` 的（胸针、戒指、项链、耳环）**不出独立图**，节点上明确显示「随人物生成 · 见角色资产」并给一个跳转到对应 character 节点的链接。这条规则错了会重演已修过的 bug。

### N5 `storyboard` 手绘故事板节点（宽 780）

```
┌─ 手绘故事板 · 镜1-6 ────────────────────────────┐
│ ┌────────┐ ┌────────┐ ┌────────┐                │
│ │ ①  ▢▢ │ │ ②  ▢▢ │ │ ③  ▢▢ │                │
│ │侧面特写，│ │抬手抓住│ │门口停下│                │
│ │闭眼仰头 │ │协议书  │ │，回头  │                │
│ └────────┘ └────────┘ └────────┘                │
│ ┌────────┐ ┌────────┐ ┌────────┐                │
│ │ ④  ▢▢ │ │ ⑤  ▢▢ │ │ ⑥ 空白 │                │
│ └────────┘ └────────┘ └────────┘                │
│                     [重出整页] [→ 下一步：分镜表]│
│                                          ≈¥0.30 │
└─────────────────────────────────────────────────┘
```
- **固定 3×2 六格，一格不许少。** 现有 bug `images.slice(0, 4)` 必须消失。
- 1 秒 = 1 格。5 秒视频 → 格 1-5 有内容、**格 6 空白且不携带六要素数据**（空白格带数据会让视频模型混乱）。
- 每格：左上角序号（读图上原有编号，前端也叠一层序号标签保证可读）、格下方一句话总结（`one_sentence_summary`）。
- 六要素不上屏（原则 6）。整页是一次生图调用产出的一张图，因此「重出整页」是唯一的重渲粒度，不提供单格重渲（会与整页排版冲突）。
- 10 秒 / 15 秒长视频的格数规则尚未定案，**本批只做 5 秒**；遇到 `duration > 5` 时节点显示「长镜头暂不支持，请拆分」而不是猜一个格数。

### N6 `shot_group` 镜头分组节点（宽 620，横条）

```
┌─ 镜头分组 · 5秒 → 2镜头 ───────────────────────┐
│ 镜头1  格1-3  3s  中景 · 固定    守轴线：左→右 │
│ 镜头2  格4-5  2s  特写 · 推镜 ★钩子           │
└────────────────────────────────────────────────┘
```

## 7. AgentDock：画布内对话框

位置：画布右下角固定浮层，可折叠、可拉宽，**不占据布局的一整栏**（三连框已永久废除，禁止以任何形式复活四栏/三栏固定网格）。

### 7.1 交互形态
Claude Code 式**问答栏**：agent 一次只问一件事，给出选项按钮 + 可选的自由输入。每个输入框里用灰字给出**记入例（即默认值）**，用户不改就采用该默认值。

### 7.2 生成流程（step 1-3，已确认的规格）

**Step 1 · 剧本解析**
用户在对话框贴剧本 → 文本模型解析 → 摘要提示三要素（故事构成 / 角色 / 分镜信息）→
- 三项齐全：问「以上信息是否正确？」→ [确认] / [继续修改]
- 有缺失：问答栏逐项补齐 → 再确认
确认后在画布上生成 `script` 节点。

**Step 2 · 资产**
先人物：问答栏「想要一个理想的〇〇」，字段 = 生成风格 / 发型 / 服装 / 体型 / 表情 / 补充描述（各带灰字例）→ 「按当前信息提交？」→ [确认] / [继续修改]。
- 确认 → 生成 `character` 节点（固定规格：纯白底、着衣、四视图、横屏，这些**写死在源码**，不问用户）
- 继续修改 → 把用户已填内容**原封不动回填**，不得清空重问
再场景：时间 / 场景情绪 / 生成风格 → 确认 → 结合 step 1 的剧本上下文生成 `location` 节点。

⚠ **喂给图像模型的提示词不是问答栏的生文**，而是文本模型抽取 + 按生成基准组装后的产物（沿用现有 `synthesize_image_prompt` 同型逻辑）。

**Step 3 · 故事板**
「是否生成手绘分镜故事板？」→ 确认 → 生成 `storyboard` 节点（1 页 6 格、横屏、1 秒 1 格、时序、编号、格下一句话总结）。

**Step 4 · 见第 9 节（文字分镜表预审）→ 第 10 节（渲染）→ 出视频**

### 7.3 agent 自动建节点 + 用户手动建节点（两者都要）
- agent 驱动：对话推进到某一步就自动在画布上落一个节点，并自动连线到上游。
- 手动：画布空白处右键 → 节点类型菜单 → 手动添加；也支持从节点右侧连接点拖出连线到空白处，松手弹出「可接的下一类节点」菜单。

### 7.4 自动落位算法（`useAutoLayout`）
- 按灵魂链路从左到右分列：script → 资产 → storyboard → shotlist_text → keyframe/shotlist_render → video。
- 同类型多个节点在同一列向下排。
- 重渲派生的节点放在来源节点**右下方偏移 (60, 40)**，用虚线边连回来源，视觉上表达「这是那一版的重做」。
- 新节点出现时把视口平滑移到它上面（不要瞬移、不要缩放突变）。
- **不得自动重排用户已经手动拖动过的节点**（用户拖过一次即标记 `pinned: true`）。

## 8. 连线规则与上游取数

## 9. 文字版分镜表前置审查（backlog ②③）—— 本批的省钱核心

**为什么**：渲染和出视频是花钱的。让用户在**还没花钱的文字阶段**先审一遍，能大幅减少抽卡。

**流程**：故事板完成后，AgentDock 问「**是否预览渲染效果？**」，选项只有两个：
- **[确认]** → 弹出**弹窗形式的文字版分镜表**给用户/客户审阅 → 审完 → [开始渲染]（此处才是原则 4 的第一道成本闸门）
- **[继续补充信息]** → 回到上一步（故事板/资产），保留已填内容

**文字版分镜表内容（`shotlist_text` 节点 + 同款弹窗，两处复用同一组件）**：

每一格一行，展开后包含：
1. 六要素（主体 / 场景 / 摄像机 / 景别 / 拍摄手法 / 灯光，均含运动过程）
2. 情绪（`emotion`）
3. 运动逻辑（`action_beats`）
4. **镜头运动设计 6 项**（来自公式 prompt，必须逐项列出，不许合并成一段话）：
   - 确定跟随对象（跟随主体）
   - 设计运动路线（走位）
   - 用镜头运动解释空间（机位 · 景别）
   - 安排主体关系变化（距离控制）
   - 设计停顿点（打破节奏）
   - 明确结尾的信息变化（释放结果）

这 6 项若后端目前未产出，本批在视频提示词合成链路（`synthesize_video_prompt`）里补齐，并落库为结构化字段 —— **不是前端编一段文案糊上去**。
